# 宁好的产品设计：从第一性原理出发

## 1. 先问：用户真正需要什么？

宁德时代海外业务的同事和领导，每天不缺新闻。他们缺的是：**在信息出现的第一时间，知道哪些变化会影响我们的决策。**

他们要做的决策大致有四类：

| 决策 | 依赖什么信息 |
|---|---|
| 去哪卖、卖给谁 | 哪里有大型储能项目、哪个开发商在招标、哪个客户在换供应商 |
| 在哪建厂、怎么合规 | FEOC、关税、1260H 清单、各国本地化要求 |
| 怎么定价 | 原材料价格、竞争对手动作、供需格局 |
| 投什么、和谁合作 | 新技术进展、上下游企业的财务状况、行业资本动向 |

所以，一条信息有没有价值，取决于三件事：

> **信息价值 = 和决策的相关度 × 意外程度 × 时效性**

普通新闻 App 只解决了「时效」。宁好要把三件事都做到。

## 2. 从需求推出产品功能

| 第一性需求 | 产品功能 | 实现方式 |
|---|---|---|
| 只看和我们有关的 | 过滤 | 先用关键词粗筛，再让 Claude 判断是否相关 |
| 一眼看懂对我们意味着什么 | 改写标题 | 从宁德时代的利益出发重写标题，而不是翻译原标题 |
| 先看最重要的 | 排序 | 影响分 1–5，头条展示 48 小时内影响最高的一条 |
| 发生了就要知道 | 播报 | 每 30 分钟抓取一次，页面每分钟检查，高影响条目推送到群聊 |
| 不能被 AI 误导 | 可追溯 | 原文要点只能摘自原文；每条都附原标题、来源、配图和链接 |
| 能直接行动 | 建议动作 | 每条给一句可执行的下一步 |

## 3. 什么不做（MVP 的边界）

先做到能演示，再逐步加功能。以下是有意不做的：

- **不建数据库**：用一个 JSON 文件存数据，提交回 GitHub 仓库。300 条情报只有几百 KB，没必要上数据库。
- **不建服务器**：网站是静态页面，托管在 GitHub Pages；定时任务交给 GitHub Actions。
- **不做登录和个性化订阅**：演示阶段，所有人看同一个情报流。
- **不追求秒级实时**：30 分钟的延迟对战略决策足够。真要秒级，需要常驻服务和付费数据源。

## 4. 关键设计决定

**为什么让 AI 改写标题，而不是只做摘要？**
摘要回答的是「这篇文章说了什么」。改写标题回答的是「这对我们意味着什么」。后者才是情报，前者只是新闻。

**为什么用结构化输出？**
Claude 的输出必须按固定表格填写（分类、信号、影响分、要点……），代码拿到的一定是合法 JSON。这样排序、筛选、推送都能可靠运行，不需要解析自由文本。

**为什么把「视角」单独写成 `lens.md`？**
视角是这个产品的核心资产，应该由懂业务的人维护，而不是埋在代码里。换一家公司，比如做比亚迪或阳光电源的版本，只需要换这一个文件。

**为什么强调「不编造」？**
情报产品最大的风险不是漏报，而是错报。一条编造的「宁德时代中标」比十条漏报更有害。所以规则要求：
- 数字和公司名必须在原文里出现
- 原文没写就说「原文未披露」
- 每条都附原文链接

## 5. 下一步可以做什么

按「价值 ÷ 难度」排序：

1. **SEC 财报披露**：跟踪 Fluence、Tesla、NextEra 等公司的 8-K、10-Q，用 EDGAR 的免费接口。
2. **事件聚合**：把多家媒体对同一事件的报道合成一条，并跟踪后续进展，形成「故事线」。
3. **中文官媒直连**：用 RSSHub 等开源项目，为没有 RSS 的政府网站生成订阅源。
4. **质量评估**：人工标注 30 条，作为测试集，每次修改 `lens.md` 后跑一遍，看准确率有没有提高。
5. **问答**：在情报库上加一个问答入口，比如问「最近三个月美国 FEOC 规则有什么变化？」。
